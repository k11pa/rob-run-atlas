Ключевые результаты чтения типов и нативных методов:

1. RandomLootObjectDescription: идентификатор, entityId, позиция, ориентация, взаимодействие и сигнализация. Состав случайного пула и веса не заданы.
2. ContainerDescription: тип, бур, время взлома, очки накопительным предметам. Содержимого сейфа и процентов в этой структуре нет.
3. LocationBuildingGroupLootDescription связывает контейнеры и узлы обыска; это не список выпадающих предметов.
4. RandomLootObjectData.Item — реплицируемое значение LootObjectItemDescription. RandomLootObjectModel.get_Item читает его; SetItem записывает уже выбранный предмет. Эти методы не раскрывают таблицу выбора. Это согласуется с управлением содержимым сервером, но не является доказательством отсутствия любых других клиентских источников.
5. WeightItems<T> и WeightedList<T> — общий механизм весов, включая пустой результат. Сам по себе он не содержит привязки «этот сейф → эти предметы». Найденное наличие алгоритма не позволяет вычислить недостающие проценты.
6. RobberAuthorityLevelDescription содержит exchangeCargoRevenueAdditiveModifier и sellLootRevenueAdditiveModifier. Эти поля изменяют выручку. На их основании нельзя заявлять увеличение шанса редкого дропа.

## Локальные исправления приложения

- scripts/build-from-db.py теперь читает acquisition_sources.drop_probability для связанных loot_point_entries и сохраняет его как probability. Раньше это поле игнорировалось даже при наличии значения в БД.
- Карточка предмета теперь использует общий вывод количества, числа действий и вероятности точки. Размещение узла отображается отдельно. Количество для одиночного предмета больше не подписывается ошибочно «за действие».
- Неизвестная/NULL вероятность не отображается как 0%. Настоящий 0 сохраняется.
- dist/data.js и dist/db.js не редактировались. Повторная полная сборка из Supabase не запускалась: в новой копии нет .env с SUPABASE_DB_URL. Для этих исправлений пересборка данных не нужна, поскольку заполненных вероятностей всё равно нет.

Проверки: `pnpm run check`, `node scripts/check-loot-probability.mjs`, синтаксический разбор Python-сборщика. В браузере проверена карточка золотого слитка и раскрытие его 8 точек. Сервер продолжает работать на localhost:3000. Коммитов и push на GitHub не было.

## Что блокирует полное заполнение

Для точного случайного дропа нужен источник самих пулов: привязка к точке/типу контейнера/зданию, предметы и количества, веса или вероятности, пустой исход, число попыток, условия уровня/тира/версии. В текущей Supabase этих значений нет; в проверенных клиентских данных они не найдены.

Следующий надёжный шаг — получить у разработчиков экспорт этих таблиц или документированный доступ к ним. Наблюдения игроков могут подтвердить место находки, но конечное число наблюдений не даёт точного конфигурационного процента. Не заполнять отсутствующие значения по редкости, названию здания, месту применения ключа или параметру появления узла.
